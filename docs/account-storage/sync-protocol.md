# Протокол обмена личным прогрессом, версия 1

Проект этапа 2. [Данные](data-contract.md), [клиентские переходы](client-lifecycle.md). Методы ниже ещё не реализованы. Корень будущего API: `/api/method/allimquran.account_storage.`; работающий endpoint не следует предполагать по этому документу.

## Сессия и транспорт

Используются cookie-сессия Frappe, HTTPS и same-origin запросы. Изменяющие методы разрешают только POST и требуют точный непустой `X-Frappe-CSRF-Token`, совпадающий с токеном серверной сессии, даже если общая проверка сайта отключена. Авторизационные и CSRF-токены не записываются в outbox, экспорт или журнал операций. `session_binding` — полученная при open привязка к текущей серверной сессии, например HMAC от sid с отдельным серверным секретом; она не заменяет cookie или CSRF и хранится только в памяти страницы.

Каждый запрос после open содержит `expected_account_id`, `epoch`, `session_binding`. Сервер сначала определяет владельца из сессии, затем сравнивает ожидаемого владельца и привязку. Несовпадение останавливает запрос до чтения чужого payload или изменения базы. Время клиента и `device_id` не являются доказательством владельца. Все ответы с данными, включая ошибки, получают `Cache-Control: private, no-store`; service worker и CDN исключают эти маршруты из кэша.

Для GET эти три поля передаются заголовками `X-Allim-Account`, `X-Allim-Epoch`, `X-Allim-Session`, для POST — полями JSON; при наличии дублирующих заголовков несовпадение отклоняется. Привязка сессии не включается в URL/логи. context не требует этих полей, open устанавливает их, а end_session проверяет владельца/привязку без зависимости от epoch, чтобы сброс прогресса не мешал выходу.

Проверены локальные исходники Frappe `763b384c5a6eb3e84151d33380433412b4f11f30`: `auth.py:83` имеет условия обхода общей CSRF-проверки, `handler.py:46` оборачивает результат в `message`, `app.py:397` коммитит успешный изменяющий запрос, исключение в `app.py` откатывает транзакцию. Собственная строгая проверка CSRF уже применяется в ALLIM `review_portal.py:129`. Это проверка локальной зависимости, не свидетельство конфигурации production.

## Методы

| Метод | Запрос и результат |
|---|---|
| `context` GET | Только `{mode: guest}` либо `{mode: account}` из текущей сессии, без персонального прогресса. Допустим Guest; не создаёт аккаунт |
| `open` POST | Для авторизованного пользователя. Идемпотентно создаёт Account State при необходимости, возвращает account_id, epoch, session_binding, schema/protocol_version, last_seq, capabilities и лимиты |
| `scan` GET | Первый запуск/восстановление кэша: постранично текущие записи по неизменяемому `(kind,id)`, включая tombstones. Передаёт scan_token, after_key; подробности ниже |
| `pull` GET | `after_seq`, необязательный `through_seq`, limit. Возвращает records, next_seq, through_seq, has_more. Данные относятся только к владельцу сессии |
| `apply` POST | `{protocol_version:1, expected_account_id, epoch, session_binding, device_id, operations:[...]}`. Результат каждой операции плюс текущий last_seq |
| `export_data` POST | Создаёт приватную выгрузку поддерживаемых данных и манифеста, с владельцем и сроком жизни; не меняет учебный прогресс |
| `download_export` GET | Только та же сессия/владелец и актуальная эпоха; без публичного File URL и без токена в URL |
| `prepare_reset` POST | Возвращает одноразовое подтверждение на 10 минут для `scope: all_personal_progress`, account_id, epoch; не удаляет данные |
| `reset` POST | Явный полный сброс с тем же scope, confirmation и reset_id. Атомарно удаляет персональные данные и меняет epoch; никогда не вызывается очисткой браузера |
| `end_session` POST | Проверяет исходную session_binding и завершает только эту текущую сессию через Frappe logout. Сменившаяся сессия даёт session_changed; метод не изменяет учебные данные |

Frappe-оболочка успешного ответа: `{"message":{...}}`. Ожидаемые прикладные ошибки имеют `message.error.code`, `retryable`, необязательный op_id; исключения фреймворка до входа в метод могут иметь другой формат. Клиент обязан сначала проверить HTTP status и не трактовать отсутствие message как пустую историю.

[protocol-examples.json](protocol-examples.json) показывает синтетические запросы, квитанции после потерянного ответа и сохранение двух вариантов дневной цели. Примеры не содержат действующих сессий и не являются результатом вызова API.

Начальные пределы API: 25 операций и 256 KiB UTF-8 тела запроса; 64 KiB на сериализованный value, 200 записей и 1 MiB на страницу чтения. Превышение даёт явную ошибку, не усечение. Для одинокой записи, не помещающейся в лимит ответа, возвращается ошибка данных, а не бесконечная пустая страница. Ограничение apply: 60 запросов/минуту на аккаунт, читающих методов: 120/минуту; 429 с Retry-After. Числа являются начальной спецификацией, нагрузочная проверка этапа 3 может потребовать отдельного изменения версии capabilities.

## Операция и квитанция

Оболочка операции: `{op_id, action, kind, id, base_version, value}`. Для удаления value отсутствует. owner, серверные version/change_seq и created_at не принимаются внутри value. `op_id` создаётся однажды и никогда не заменяется при timeout, reload, offline или повторном входе. Hash операции вычисляет сервер по разобранным разрешённым полям с сортировкой ключей и неизменным порядком массивов; UTF-8, без NaN, без Unicode-нормализации пользовательского текста. Ключевые параметры хеша: protocol_version, epoch и вся операция; session_binding и текущая cookie в хеш не входят.

| `action` | Семантика |
|---|---|
| `create` | base_version=0, запись отсутствует. Тот же ID с другим содержимым даёт id_conflict; tombstone не считается отсутствием |
| `put` | Полная замена value одной изменяемой записи с совпавшей base_version; нельзя редактировать learning_event, baseline, conflict или import_receipt этим действием |
| `delete` | Совпавшая base_version, value удаляется. Для learning_event означает аннулирование и пересчёт; reading_cycle должен быть пустым |
| `restore_membership` | Только bookmark/review_item, версия актуального tombstone; новый осознанный выбор пользователя. Автоматический retry этим действием запрещён |
| `resolve` | Для конфликтов: актуальная версия целевой записи, полный список открытых conflict ID/версий и выбранный value либо `resolution: delete`. Обновление цели и закрытие конфликтов атомарны |
| `import_item` | import_id, source_digest, mapping_version, import_item_id, выбранное преобразованное value; проверяет правила переноса из контракта данных |

`delete` не может обойти открытые конфликты: возвращает unresolved_conflicts, интерфейс предлагает решение со списком сохранённых вариантов. Для служебных типов обычные create/put/delete закрыты. Импорт ограничен разрешёнными полями, типами и счётчиками; это не универсальный обход валидации. Перед import_item клиент выполняет `begin_import` через apply: передаёт source_id, source_digest, mapping_version; сервер создаёт/читает manifest и возвращает canonical_source_id. После этого клиент фиксирует ID элементов в локальном манифесте. Этот action не переносит учебные данные сам по себе и тоже имеет op_id/квитанцию. Изменение baseline после переноса требует отдельного будущего процесса восстановления и не доступно через put.

Квитанция `(account_id, epoch, op_id)` хранится в базе весь срок эпохи, не в краткоживущем Redis. Результаты: `applied`, `noop`, `conflict`, `rejected`; повтор добавляет `replayed:true`, не создаёт новую квитанцию. Квитанция содержит hash, outcome, затронутые ID/версии/change_seq и код ошибки; приватный текст не дублируется. Актуальные записи клиент получает pull. Повтор op_id с другим hash даёт `op_id_reused`, исходная квитанция не меняется.

Для create learning_event дополнительно уникален смысловой ключ попытки. Новое op_id с тем же ключом и тем же событием возвращает noop + исходный event ID; иной payload даёт event_conflict. Это не эвристическое сравнение текста чтения: два настоящих повторения с разными attempt_id учитываются оба.

## Транзакция и конкурентные запросы

1. До обработки payload проверить метод, сессию, владельца, привязку, CSRF, формат и предел тела. Для первого open сериализовать создание через блокировку существующей строки User; уникальный индекс на user/account_id остаётся страховкой гонки. Не использовать ненадёжное «SELECT пусто → INSERT» без обработки конкуренции.
2. Заблокировать Account State данного владельца `FOR UPDATE` и проверить epoch внутри блокировки. Все пути изменения, reset и построение экспорта соблюдают этот порядок блокировок.
3. Для каждой операции проверить квитанцию; затем тип, смысловой ID, base_version и доменные ограничения. Квитанция, запись, связанные конфликты/проекции и индекс изменений записываются одной транзакцией.
4. Каждой изменившейся записи назначить следующий seq внутри той же блокировки. Изменение нескольких записей одной операцией получает несколько последовательных seq; запись сохраняет последний свой seq. Ни один seq не виден раньше commit.
5. Для ожидаемой ошибки отдельной операции использовать savepoint: откатить её частичные изменения и сохранить rejected-квитанцию. Корректные независимые операции той же пачки можно применить. Неожиданная ошибка базы откатывает всю пачку и все квитанции; клиент повторяет те же op_id. Между элементами пачки не делать commit.
6. Вернуть результаты. Frappe завершает транзакцию до доставки успешного ответа. Сбой после commit, но до ответа безопасен за счёт постоянной квитанции. Очередь нельзя удалять лишь потому, что отправка запроса завершилась на уровне браузера.

Пачка содержит независимые пользовательские операции. Составное действие, которому нужна атомарность, выражается отдельным доменным action, как resolve, а не предположением «вся пачка обязательно успешна». Повтор rejected/conflict с тем же op_id сохраняет прежний результат; после решения причины создаётся новая операция. Необходимые базовые ограничения: unique(user) для Account State; unique(account,epoch,kind,id), unique(account,epoch,op_id), unique(account,epoch,seq), unique(account,epoch,event_key), unique(account,epoch,import_item_id) и unique(account,reset_id) для отдельной reset-квитанции.

## Получение изменений и восстановление кэша

Индекс изменений содержит seq, kind, id и серверную дату, но не старые payload. pull читает ограниченный диапазон `(after_seq, through_seq]`, выбирая through_seq = текущий last_seq при первом запросе. Для ключей из страницы возвращает текущие полные записи, включая tombstone. Несколько изменений одного ключа допускают один возвращённый record. `next_seq` — последний просмотренный seq индекса, а не максимальный change_seq в ответных records.

Текущая запись может оказаться новее through_seq, если её изменили во время чтения. Это допустимо: клиент хранит наибольший change_seq каждой записи и игнорирует более старую копию; cursor всё равно продвигается только до next_seq просмотренного диапазона. Полученная более новая запись не позволяет пропустить изменения других ключей. После доставки всех изменений устройства сходятся к одному состоянию; произвольная промежуточная страница не является согласованным экспортом на определённый момент.

Для нового устройства open начинает bootstrap: фиксирует H0=last_seq и выдаёт подписанный scan_token с account, epoch, H0, сроком 30 минут. scan обходит все текущие записи по неизменяемому `(kind,id)`, передавая after_key. Вставка «позади» уже просмотренного ключа или удаление после чтения попадут в индекс изменений после H0. После последней страницы фиксируется H1 и выполняется pull от H0 до H1. Сканированные записи и cursor публикуются как готовый кэш лишь после этого догоняющего чтения; незавершённый bootstrap хранится отдельно. Записи не исчезают из scan физически в пределах эпохи — остаются tombstones. Просроченный token требует начать scan заново; outbox при этом сохраняется.

Проверка scan_token включает владельца, эпоху, сортировку и after_key; курсор не позволяет выбрать другой аккаунт. Время H0 не может выйти за окно хранения индекса за 30 минут. Если восстановление базы изменило доступную границу, даже действующий token получает cursor_expired. В pull верхняя граница не превышает last_seq; after_seq из будущего отклоняется. Пустая страница не выдаётся за конец, пока has_more=true.

Индекс изменений хранится 90 дней. Если after_seq старше доступной границы, сервер возвращает `cursor_expired`, а клиент повторяет bootstrap с сохранением outbox. Маркеры удаления, смысловые ID событий и квитанции не удаляются вместе с индексом. Поэтому старое устройство не может воссоздать запись с base_version=0. Запросы epoch до reset получают `epoch_changed`; их данные автоматически не перебазируются.

Клиент применяет полученные записи и новый cursor в одной транзакции IndexedDB. Его UI строится из подтверждённых записей плюс отдельного слоя локальных намерений. Pull никогда не затирает неотправленный текст, а optimistic value никогда не объявляется подтверждённой серверной записью.

## Таблица конфликтов

| Ситуация | Решение |
|---|---|
| Разные заметки, события, записи чтения | Независимо сохранить обе |
| Та же операция после потерянного ответа | Вернуть квитанцию; не менять версии/счётчики |
| Новое завершение с тем же attempt_id | Дедупликация по смысловому ключу |
| Одновременные настройки разных имён | Независимые записи, оба изменения проходят |
| Та же настройка, цель, план или текущий хатм | Первая CAS-запись проходит; второй вариант сохраняется как conflict, пользователь выбирает; часы устройства не определяют победителя |
| Одновременная правка одной заметки/записи чтения | Сохранить серверную версию и отдельный proposed_value в conflict, показать варианты на устройствах владельца; resolve проверяет актуальные версии |
| Повтор put совпадает с текущим value | noop, даже при старой base_version, если запись жива; нового конфликта и версии нет |
| Одновременное добавление одной закладки | Если она уже существует, noop с существующей позицией; изменение порядка требует отдельного put |
| Удаление закладки и старое добавление | Tombstone запрещает create; восстановление только с прочитанной версией удаления |
| Снятие review_item после чтения и новая ручная постановка | Конфликт версий оставляет более новую очередь, само событие чтения сохраняется |
| Удаление и устаревшая правка текста | Tombstone запрещает восстановление; proposed текст остаётся локальной копией для явного сохранения как новой заметки, на сервер скрыто не возвращается |
| Фоновое сохранение старой позиции чтения | Серверная позиция побеждает; намерение завершается как конфликт без отдельной серверной conflict-записи/диалога |
| Несколько старых агрегатов с возможным перекрытием | Не складывать/не подменять; импорт отчётливо сообщает пропуск спорного агрегата |

При повторном разрешении конфликта после чужой правки сервер выдаёт conflict_again, выбранный текст сохраняется локально. Отказ от варианта не удаляет основной record. Закрытый conflict сохраняет только метаданные решения, не пожизненную копию частного текста.

## Ошибки, удаление и экспорт

| Код/статус | Действие клиента |
|---|---|
| 401 / session_required | Остановить отправку, заблокировать аккаунт, сохранить очередь исходного владельца |
| 403 / csrf_invalid, session_changed | Не повторять запись без обновления контекста сессии |
| 409 / account_changed | Скрыть старый аккаунт; открыть новый только после проверки; чужую очередь не отправлять |
| 409 / epoch_changed | Изолировать старую очередь для восстановления; загрузить новую эпоху; без автоматического импорта |
| 409 / cursor_expired | Bootstrap, сохранив локальные операции |
| rejected / version_conflict, deleted, validation_error, clock_invalid | Сохранить намерение/результат, предложить предметное исправление; бесконечный retry запрещён |
| 413 или 429 | Уменьшить пачку без изменения операций либо соблюдать Retry-After; слишком большая отдельная запись требует исправления |
| timeout, 5xx, ошибка сети | Повтор неизменённых операций с задержкой 1/2/4/8/… максимум 60 секунд и случайным разбросом; после восстановления видимости/сети проверить сессию |

Обычное удаление записи стирает её value и оставляет tombstone; не создаётся скрытая история прежнего текста в журнале изменений или квитанции. Открытые текстовые конфликты удаляются при подтверждённом resolve-delete. Подтверждённый экспорт создаётся под блокировкой аккаунта как согласованная приватная копия; лимит 50 MiB, при превышении — явная ошибка и отдельный потоковый механизм до выпуска для таких аккаунтов. Файл живёт не более часа, проверка срока/владельца выполняется при каждом скачивании, очистка файлов — фоновая. Новая обычная редакция/удаление инвалидирует ранее созданные выгрузки; reset удаляет их. Выгрузка включает данные, версии схемы и стабильные ID, но не sid/CSRF/session_binding, auth-токены, очередь другого аккаунта, сырые аудио или секреты согласия.

Полный reset атомарно меняет epoch и удаляет Progress Record/Operation/Change старой эпохи и приватные экспортные файлы; Account State и отдельная reset-квитанция сохраняют old_epoch, new_epoch, reset_id. Повтор с тем же reset_id и тем же владельцем возвращает прежний new_epoch после аутентификации, даже если подтверждение уже использовано; другой reset_id со старой эпохой отклоняется. Одна успешная reset-транзакция не может уничтожить данные, созданные уже в новой эпохе. Удаление файлов планируется через надёжную задачу после commit; доступ к ним блокируется сменой эпохи немедленно.

Обычная очистка устройства не отправляет delete/reset. Уже выполняющийся запрос может успеть commit до серверного logout: клиент не обещает его отмену через AbortController. Поздний ответ допускает обновление только своего исходного контекста, никогда текущего другого аккаунта. Удаление из рабочей базы не означает немедленного уничтожения уже существующих резервных копий сайта; срок и восстановление резервных копий фиксируются при подготовке выпуска, без обещания, которого инфраструктура пока не подтверждает.
