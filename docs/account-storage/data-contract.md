# Контракт личных данных ALLIM, версия 1

Этап 2, 14 сентября 2026. Это проект для реализации этапов 3–6, а не описание уже работающего API. Основание: [объём этапа 1](scope.md), [инвентаризация](legacy-storage.md), приложение `6a9775e` и коммит подготовки `5de2be9`. Протокол доставки — в [sync-protocol.md](sync-protocol.md), поведение браузера — в [client-lifecycle.md](client-lifecycle.md).

## Границы хранения

Гостевой прогресс принадлежит локальному профилю браузера. Прогресс вошедшего пользователя принадлежит аккаунту на сервере; IndexedDB хранит его рабочую копию и неотправленные операции. Learn и Academy используют один слой данных. Подтверждение сервера означает сохранение в аккаунте; успешная локальная транзакция означает только сохранение на устройстве.

Владелец определяется из существующей сессии Frappe. Отдельная регистрация, таблица паролей или публичный идентификатор пользователя в URL не нужны. Сервер сопоставляет `frappe.session.user` с постоянным случайным `account_id`; переименование User не меняет этот ID, удаление и новая регистрация создают другой. Переданный клиентом `expected_account_id` служит проверкой совпадения, но не выбирает владельца.

Запись в аккаунте не является оценкой преподавателя. `self_reported`, `client_alignment` и `legacy_import` обозначают происхождение, а не доверенную оценку. Текущие курсы, зачисления, заявки и оценки Frappe/LMS остаются в своих таблицах. Микрофонные записи, исследовательское согласие и его токены, фото Ляуха и секреты авторизации не входят в этот контракт.

## Общий формат

| Поле серверной записи | Правило |
|---|---|
| `schema_version` | Целое `1`; версия формата записи, отдельно от версии API и схемы IndexedDB |
| `kind`, `id` | Тип из реестра ниже и постоянный ID; уникальность внутри `(account_id, epoch, kind, id)` |
| `version` | Целое от 1, увеличивается сервером только при изменении этой записи |
| `change_seq` | Порядок изменения внутри аккаунта и эпохи; назначается транзакционно сервером |
| `created_at`, `updated_at` | UTC-время сервера; не подменяют дату пользовательского действия |
| `deleted` | Маркер удаления. Удалённая запись сохраняет ID, версию и метаданные, `value: null` |
| `value` | Объект с полями своего типа; неизвестные поля отклоняются, а не обрезаются |

`epoch` — случайный UUID поколения данных аккаунта. Он меняется только при явном полном сбросе; старые очереди не могут восстановить удалённую историю. Создание имеет `base_version: 0`, изменение/удаление — последнюю прочитанную версию. Версии и счётчики ограничены безопасными целыми JavaScript (`0..9007199254740991`), boolean не принимается как число. Нет NaN, Infinity, дублирующихся JSON-ключей и произвольного исполняемого содержимого.

Новые пользовательские записи и операции получают UUID v4 через криптографический генератор и сохраняются до первой попытки отправки. `Date.now()` не является ID. Для единственного значения ID задаётся контрактом, например `preference/language`, `bookmark/2:255`. Удалённый случайный ID не используется заново. Повторное добавление закладки использует её постоянный ID, но требует актуальную версию маркера удаления.

Канонические ссылки: `verse_key = surah:ayah`, `word_key = surah:ayah:word`, страница `1..604`, набор страниц `hafs-madinah-604-v1`. Сервер проверяет существование аята, слова и принадлежность странице по закреплённым данным Корана; регулярного выражения недостаточно. `total_words` вычисляется по этому набору, не принимается на веру от клиента. Декоративный знак конца аята не считается словом.

Для нового действия: `occurred_at` — UTC ISO 8601 с миллисекундами, `local_date` — календарная дата на месте действия, `utc_offset_minutes` — смещение к UTC, `time_zone` — IANA-зона либо null. Проверяется согласованность даты и смещения; при наличии зоны — также смещения и зоны. Будущее более чем на 24 часа относительно сервера даёт `clock_invalid`, операция остаётся для исправления. У старой записи допустимы неизвестное время и зона: дата сохраняется как известна, UTC-полночь вместо неизвестного времени не выдумывается. Время клиента не используется для разрешения конфликтов текста и настроек.

## Реестр данных

Все `value` ниже — самостоятельные записи. Обозначение `?` означает необязательное поле; обязательность, пределы и допустимые значения уточняются в этом документе. Общие служебные поля повторять внутри `value` нельзя.

| `kind` и ID | Поля `value` | Изменения |
|---|---|---|
| `reading_cycle`, UUID | `label?`, `dataset_id` | Создать; изменить подпись по версии; удалить только пустой цикл |
| `reading_entry`, UUID | `cycle_id`, `local_date`, `occurred_at?`, `time_zone?`, `utc_offset_minutes?`, `source`, `evidence`, `parts[]`, `import_item_id?` | Создание, редакция и удаление по версии |
| `reading_plan`, `current` | `cycle_id`, `deadline` (дата или null) | Изменять согласованной парой по версии; параллельное начало двух хатмов требует выбора текущего, записи обоих сохраняются |
| `reading_past`, `baseline` | `completed_cycles`, `provenance?` | Явно введённое число прошлых хатмов без истории; CAS-редакция, отдельно от наблюдаемых завершённых циклов |
| `bookmark`, `verse_key` | `position` | Добавление/удаление по версии; ключ является ссылкой на аят |
| `review_item`, `verse_key` | `position` | Такое же правило; автоматическое снятие после повторения тоже проверяет версию |
| `preference`, имя настройки | `selected` | CAS для каждой настройки отдельно; пары режима и явного выбора — одна запись |
| `daily_goal`, `current` | `sessions` | Целое из `1,2,3,5`; это действующая цель, не число страниц |
| `reading_position`, `last` | `verse_key` | Последнее открытое место; конфликт фоновой позиции уступает серверу без диалога |
| `academy_plan`, `current` | `minutes`, `focus`, `target` | Объект целиком по версии: 10–45 минут, focus `recitation/memorization/arabic/tafsir`, target до 2000 символов |
| `academy_diagnostic`, `current` | `level`, `goal`, `minutes`, `answered_at`, `route` | Объект по версии: level `letters/assisted/independent`, goal `reading/tajwid/hifz`, 10–30 минут |
| `reflection`, UUID | Поля заметки ниже | Полная редакция по версии; обе версии при конфликте сохраняются до решения |
| `learning_event`, UUID | Общие поля времени, `event_type`, `attempt_id`, поля события ниже | Неизменяемое событие; повтор доставки не добавляет событие. Исправление — явное аннулирование с пересчётом |
| `activity_baseline`, `totals` | `sessions`, `words_reviewed`, `hints`, `provenance` | Исходные агрегаты без выдуманной истории |
| `activity_day_baseline`, дата | `count`, `provenance` | Старый счётчик за известный локальный день |
| `hifz_unit_baseline`, `verse_key` | `week_counts[3]`, `maintenance_count`, `maintenance_level`, `started_at`, `last_accepted_at`, `completed_at`, `next_review_at`, `permanent`, `provenance` | Исходный снимок аята; не заменяется присланным полным состоянием при обычной синхронизации |
| `hifz_day_baseline`, `verse_key/local_date` | `count`, `provenance` | Отдельная запись для каждой даты старого unit.daily |
| `hifz_page_baseline`, номер страницы | `connected_attempts`, `connected_reviews`, `last_connected_at`, `sealed_at`, `permanent`, `provenance` | Исходный снимок страницы |
| `conflict`, UUID | `target_kind`, `target_id`, `base_version`, `observed_version`, `proposed_value`, `source_op_id`, `status` | Создаёт сервер; `open/resolved`, завершённый конфликт лишается текстового payload |
| `import_manifest`, ID набора | `source_digest`, `mapping_version`, `canonical_source_id` | Небольшая серверная запись для распознавания того же набора, без всей исходной истории |
| `import_receipt`, ID элемента импорта | `import_id`, `import_item_id`, `source_key`, `target_kind`, `target_id`, `outcome` | Отдельный результат одного элемента; итоговый отчёт читается постранично |

`position` — сохраняемый целый порядок внутри закладок или очереди. Первый импорт назначает `0..n-1` в порядке старого массива; новое добавление получает текущее минимальное значение минус 1. При равенстве сортировка по ID даёт одинаковый порядок на устройствах. Перемещение всех элементов одним снимком не поддерживается; изменение позиции отдельного элемента требует его версии.

`reading_entry.parts[]`: 1–604 уникальных страниц, каждая `{page, full, word_keys}`. При `full: true` список слов пуст; при `false` — непустой список уникальных канонических слов этой страницы. `source` — `paper/digital/mic`, `evidence` — `self_reported/client_alignment/legacy_import`; для нового mic допустимо только `client_alignment`. Размер записи ограничен также общим лимитом API. Длинная сессия разбивается на самостоятельные записи с сохранёнными ID до отправки. Переделывание ID при сетевом повторе запрещено.

Покрытие цикла — объединение страниц/слов всех его неудалённых записей; повторы увеличивают объём практики, но не уникальное покрытие. Завершённый цикл — покрытие всех 604 страниц. Итог хатмов = `reading_past.completed_cycles` + число завершённых циклов. Редакция или удаление записи пересчитывает результат. `past` из preview не трактуется как перечень циклов. Поля `letters` и расчёты награды не входят в новую модель.

Настройки: `language` хранит предпочтение из поддерживаемого сайтом набора языков; страница с меньшим набором использует локальный fallback, не переписывая предпочтение. `arabic_size` — целое 34–66; `show_meaning`, `audio_repeat`, `show_interlinear`, `auto_advance`, `sound_cues`, `strict_correction` — boolean. `selected_reciter`, `mushaf_font`, `mushaf_paper`, `mushaf_ink` — значения существующего реестра приложения, публикуемого в `open.capabilities`; клиент не придумывает новые. `recitation_flow.selected = {mode, explicit}` сохраняет пару старых полей; mode берётся из того же реестра. Неизвестная настройка требует совместимой версии клиента. Отсутствующая запись означает текущий продуктовый default; открытие страницы не загружает defaults на сервер как пользовательский выбор.

Начальный реестр перечислен в [capabilities-v1.json](capabilities-v1.json): 16 языков главной, 11 ID чтецов, варианты оформления, режимы и trigger заметки. Он сверяется с main при реализации; добавление языка из PR #2 требует отдельного содержательного изменения. Язык, отсутствующий в текущем реестре, не заменяется молча при импорте — исходник остаётся для разбора.

`academy_diagnostic.route` вычисляет сервер: letters → foundation, иначе goal hifz → hifz, tajwid → tajwid, иначе reading. Диагностика не перезаписывает минуты или цель плана. Это самоописание ученика, не результат экзамена.

`reflection.value`: `verse_key`, `reference`, `reflection`, `action`, `fawaid_id`, `fawaid_scholar`, `fawaid_benefit`, `fawaid_source_url`, `trigger`, `review_at`, `completed`, `completed_at`, `authored_at`, `edited_at`. Поля контекста источника/даты могут быть null; хотя бы reflection или action непустое. Текст reflection/action — до 10000 символов каждый, benefit — до 10000, reference/scholar — до 1000, остальные строки — до 2000. Общий предел записи тоже обязателен. URL только http/https, вывод через текстовые DOM-операции, без исполнения HTML. Trigger соответствует четырём текущим значениям формы. `completed` не предполагает известное `completed_at` в старой записи. Новая отметка выполнения записывает его явно. Ссылка на источник не даёт права читать чужие заметки.

## События, агрегаты и хифз

Для действий после перехода на новый слой создаются события, а не присылаются новые суммарные числа. Один завершённый проход даёт одно `verse_completed`; один клик подсказки — одно `hint_used`. Пара `(attempt_id, event_type)` уникальна для завершения аята и начала/завершения связной страницы; для подсказок добавляется `hint_index`. Это защищает от случайной повторной финализации даже с новым `op_id`. Новый реальный повтор получает новый `attempt_id`.

| `event_type` | Дополнительные поля и эффект |
|---|---|
| `verse_completed` | `verse_key`, `mode: read/memory`, `matched_words`, `hints_used`, `full_verse`, `alignment_complete`, `evidence: client_alignment`, `ruleset: current-300-v1`. +1 session, +matched_words, +1 activity за local_date; хифз только при тех же условиях, что в действующем клиенте |
| `hint_used` | `verse_key`, `hint_index >= 1`; +1 hint независимо от последующего завершения попытки |
| `connected_started` | `page`, `ruleset`; +1 connected_attempts |
| `connected_completed` | `page`, `ruleset`, `ordered_verse_keys`, `without_hints`, `alignment_complete`; закрепление/повтор страницы по текущим условиям |

Сервер проверяет согласованность флагов, канонические ссылки, предел matched_words и допустимые переходы; он не выполняет повторное распознавание по этим полям и не называет результат проверкой преподавателя. Журнал, закладка и событие завершения — разные сущности: запись страницы вручную не увеличивает хифз или sessions. Автоматическое снятие из review_queue — отдельная CAS-операция; её конфликт не откатывает состоявшееся чтение.

Текущие условия извлекаются из `recordRecognitionSession`, `finishMemorySession`, `recordHeartRecitation`, функций связной страницы в `learn/javascript.js`. Сохранить 3×100, 20 поддерживающих повторов, интервалы 30/60/90/180/365 дней и исключение подсказки/неполного аята; не подключать fuzzy-движок preview. Проектирование хранения не разрешает менять критерий принятия речи.

Обычное полное чтение тоже может давать зачёт хифза: это действующее поведение `completeRecognizedVerse`. Адаптер должен сохранить оба пути — read и memory — с одним событием завершения на попытку. Поддерживающий интервал начинается в 12:00 местного дня по текущему addHeartReviewDays; перевод в UTC не должен превратить его в прибавление фиксированных 24 часов через переход летнего времени.

Проекция хифза строится из единственного активного исходного снимка аята/страницы и уникальных событий после локального перехода. Порядок событий фиксирован `(occurred_at, event_type_order, id)`, где connected_started=0, hint_used=1, verse_completed=2, connected_completed=3; arrival time не влияет на результат. Для календарных интервалов используется зона события, при её отсутствии фиксированное смещение. Позднее offline-событие вызывает пересчёт затронутого аята/страницы и может уточнить дату следующего повторения; исходное событие при этом не теряется. Зачёт связной страницы проверяется на состоянии её аятов к моменту события, а не на сегодняшнем итоге. Повторный пересчёт не меняет факты чтения и не создаёт дополнительные события. Реализация этого reducer и его соответствие действующим одиночным сценариям — обязательная проверка этапов 3–4.

Итоги sessions/words/hints = единственный старый totals + сумма эффектов неудалённых событий. Дни = старые day-baselines + события с их сохранённым local_date. `daily` внутри хифза и общая активность — разные показатели; их нельзя складывать между собой. Импортированные week_counts не суммируются с accepted: при отсутствии массива accepted раскладывается по трём ступеням действующим нормализатором.

Аннулирование события требует его текущую версию и пересчитывает зависимые итоги, не изменяя остальные события. Смысловой ключ аннулированного события остаётся занятым до смены эпохи: повторная доставка не восстанавливает его. Редактор замены событий и восстановления спорных старых агрегатов не входит в первый выпуск; это отдельная будущая функция, которой потребуется свой контракт.

## Перенос существующего состояния

[target-mapping.json](target-mapping.json) закрепляет назначение всех 27 полей и отдельных ключей. Сырая резервная копия создаётся до преобразования и остаётся локально; неизвестные поля и токены не попадают на сервер. Конвертер возвращает список перенесённого, пропущенного и спорного, а не молча приводит всё к defaults.

Для legacy назначаются стабильный `source_id` в локальном манифесте и хеш исходных поддерживаемых данных. ID каждого импортируемого элемента детерминирован из `source_id`, типа и старого ключа; для одинаковых timestamp-ID с разным содержимым используется сохранённый индекс исходной записи. Манифест резервной копии хранит эти ID, поэтому повтор её импорта не создаёт новые записи. Серверный `import_item_id` уникален для аккаунта и эпохи; другая копия с тем же digest и mapping_version обнаруживается как повтор. Совпадение старого ID без совпадения содержимого не означает одну запись.

`provenance = {source_id, source_digest, mapping_version:1, legacy_key}`. Digest — SHA-256 канонического поддерживаемого содержимого до преобразования, без токенов/сырых записей. `import_id = "import:" + SHA256(JSON([source_digest, 1]))`; ID элемента и новой импортированной сущности = `"import:" + SHA256(JSON([canonical_source_id, kind, legacy_key, occurrence_index]))`. JSON в этих формулах — компактный UTF-8 массив, без экранирования Unicode, index целое от 0. Это отдельное пространство ID от новых UUID. Manifest атомарно закрепляет первый source_id для данного digest/mapping_version; повтор с другим source_id получает исходный canonical_source_id и те же ID/квитанции, а не новую историю. Один исходный профиль с обновлённым снимком сохраняет source_id и прежние ID; изменённое содержимое занятого ID рассматривается как конфликт импорта. Сходство двух разных снимков без общего манифеста не доказывает отсутствие дублей — такие источники требуют сравнения до переноса.

Сервер проверяет формат, соответствие манифесту и уникальность, но не считает digest доказательством истинности пользовательских показателей. Неотрицательные legacy-счётчики проверяются на safe integer; week_counts ограничены 0–100, maintenance_count — 0–20. Ошибочные типы/даты перечисляются в отчёте переноса. Новые guest-записи с UUID переносят существующие ID без преобразования; формулы выше относятся только к legacy.

Гостевые данные нового формата уже имеют устойчивые ID. В момент подтверждения фиксируется список выбранных записей и их локальные версии; позднейшие гостевые изменения в другой вкладке в него не включаются. Отдельные `import_receipt` отражают результат каждого элемента. Старая копия не удаляется при частичном результате.

Начальные агрегаты устанавливаются только там, где нет baseline и событий соответствующего показателя/аята/страницы. Если две старые копии могут перекрываться, автоматические сумма, max и замена запрещены. Первая версия импорта сохраняет аккаунт, сообщает о конфликтующем агрегате и оставляет исходную копию для отдельного разбора; не выдаёт такой элемент за перенесённый. Уникальные заметки/чтения и отсутствующие закладки можно перенести независимо. Настройки, план и позиция с уже существующим значением меняются только после выбора пользователя и проверки версии.

Preview journal с `allim-reading-sync-v1.user` другого владельца не предлагается как гостевой импорт. Recovery-копии не конкатенируются. Дополнительные методы хифза, фото и сырой архив PR #2 сохраняются на месте, но не входят в активные сущности.

## Границы реализации этапа 3

Серверные таблицы/DocType: `ALLIM Account State` (User link, account_id, epoch, last_seq), `ALLIM Progress Record` (одна типизированная запись), `ALLIM Progress Operation` (квитанция идемпотентности), `ALLIM Progress Change` (индекс изменений). Конфликты и результаты импорта — типы Progress Record. Для служебных процессов отдельно нужны `ALLIM Progress Reset` (постоянная квитанция сброса, без учебного payload) и `ALLIM Progress Export` (владелец, эпоха, срок, статус и путь приватного файла). JSON разрешён для одной ограниченной записи, но не для всей истории аккаунта. Legacy daily-словари разбиваются на hifz_day_baseline; лимиты не обходятся сжатием в одно поле. Смысловой event_key и import_item_id сохраняются отдельными индексируемыми колонками даже после очистки value при удалении.

Внешний REST-доступ к этим DocType для обычных пользователей закрыт. Чтение, запись, поиск, экспорт и удаление идут через API с проверкой владельца; generic `/api/resource`, отчёты, sharing, стандартные DocType Version и логи не должны раскрывать payload. Техническое администрирование и резервные копии сайта — отдельные полномочия. Целевая версия Frappe — 16 согласно pyproject.toml; индексы, конкурентное создание аккаунта, транзакции и права проверяются на реальной базе на этапе 3.
