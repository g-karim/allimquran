# Дополнительная проверка Firefox и Safari

15 сентября 2026. Проверяется приложение из `6ffdad0` на полном отдельном
сайте `allim-release.localhost`, описанном в [этапе 7](release-stage7.md).
Production не обновлялся. Изменены только тестовые скрипты и документация.
**Браузерный допуск к выпуску не получен:** найден воспроизводимый сбой первого
открытия аккаунта в нескольких вкладках; физический Safari/iOS ещё не проверен.

## Firefox: запуск и результат

Playwright 1.63.0, Firefox 155.0 (build 1543), macOS 27.0 (26A428).
Прежний отказ `Could not find profile folder` воспроизводился даже с явно
созданным пустым профилем. Он соответствует описанному у Mozilla поведению
прямого запуска на macOS 27: Firefox пытается обратиться к защищённому обычному
каталогу приложения ещё до использования тестового профиля
([Mozilla bug 2060476, comment 7](https://bugzilla.mozilla.org/show_bug.cgi?id=2060476#c7)).

Для тестового процесса заданы отдельные пустые `MOZ_APP_DATA` и
`MOZ_LOCAL_APP_DATA`. Пользовательский профиль не читался, настройки защиты
macOS не менялись. Затем выявился отдельный сетевой фактор: Firefox использовал
системный прокси для loopback. В пяти браузерных скриптах, принимающих только
локальный fixture URL, добавлено `network.proxy.type=0` для Firefox. Системные
настройки прокси не менялись; браузер после этого получил настоящий HTTP 200
от локального Frappe.

| Набор | Итог Firefox |
|---|---|
| Хранение и смена аккаунтов | 15 групп прошли; группа одновременного первого открытия упала; следующие 4 не выполнены в этом прогоне |
| Перенос legacy | 7 групп прошли |
| Журнал | 5 групп прошли |
| Перезапуск, мобильные языки, форма входа, LMS | 4 группы прошли |

Итого 31 группа прошла. Полный набор хранения не прошёл. Ранее пройденные
проверки Chromium/WebKit не отменяют обнаруженную гонку: её проявление зависит
от порядка параллельных запросов.

Проверены настоящий matcher с контролируемым результатом распознавания,
повторный зачёт, ручная запись и исправление, конфликт редакций журнала,
гостевой перенос, изоляция аккаунтов, автономная очередь при загруженной
странице и повторная доставка. Полностью закрыт и повторно запущен процесс
Firefox с тем же профилем: гостевая запись IndexedDB сохранилась, POST личных
данных гостя не было. EN/RU/AR показаны на ширине 390 px; снимки RU/AR просмотрены,
горизонтального переполнения журнала нет. Это desktop Firefox с узким viewport,
не Firefox на телефоне и не проверка реального микрофона.

В тестах исправлены самостоятельные предположения о браузере:

- Проверка отложенного ответа теперь дожидается подтверждённого владельца B
  и проверяет его account scope, прежде чем считать пустую историю доказательством
  изоляции. Следующий quota-сценарий начинается после завершения смены владельца.
- `DOMException.name` проверяется внутри страницы: транспорт Playwright для
  Firefox передавал `Fixture quota` без имени `QuotaExceededError`. Проверка
  ошибки и сохранности экспортируемого черновика сохранена.
- При смене аккаунта журнал проверяет итогового владельца и закрытую приватную
  форму. Ожидание одного события навигации давало `NS_ERROR_FAILURE` при замене
  уже начавшейся навигации. Итоговые проверки владельца B и отсутствия записи A
  в повторном прогоне прошли.

## Обнаруженная гонка CSRF: открытый дефект

`allimquran.account_storage.context` вызывает `frappe.sessions.get_csrf_token()`.
В свежей сессии токена ещё нет. При одновременном обращении несколько запросов
создают и сохраняют разные значения; последующие POST используют токен из своего
GET, который уже мог стать устаревшим. Frappe отклоняет такой запрос ещё до
обработчика ALLIM с HTTP 400 / `CSRFTokenError`. Клиентское первоначальное открытие
не восстанавливается от этой ошибки, поэтому вкладка может остаться без готового
хранилища. Это не специфическая ошибка движка Firefox.

Отдельный HTTP-тест дважды воспроизвёл: шесть параллельных первых GET context
одной новой сессии → шесть разных токенов → пять POST open с 400 и один с 200.
Все ответы сохранили `no-store` и отсутствие Set-Cookie; утечка аккаунта этим
сценарием не обнаружена. Проверка выполнялась только на синтетическом локальном
пользователе. На production новый API отсутствует.

Добавлен [check_account_session_start.py](../../scripts/check_account_session_start.py):
он **сейчас завершается с ошибкой**, фиксируя открытый дефект. Не следует
превращать его в зелёный предварительным последовательным запросом context,
отключением CSRF или ослаблением проверки токена. Исправление инициализации
сессии/восстановления клиента — отдельный следующий шаг; в этом аудите приложение
не изменялось.

```sh
/absolute/fixture-bench/env/bin/python scripts/check_account_session_start.py \
  --credentials /private/fixture-credentials.json --user b
```

## Воспроизведение Firefox

Нужны полный локальный fixture site, Redis и два синтетических пользователя из
этапа 7. Скрипты изменяют только их тестовый прогресс; production URL запрещён.

```sh
mkdir -p /tmp/allim-firefox-fixture-appdata /tmp/allim-firefox-fixture-cache
MOZ_APP_DATA=/tmp/allim-firefox-fixture-appdata \
MOZ_LOCAL_APP_DATA=/tmp/allim-firefox-fixture-cache \
ALLIM_PLAYWRIGHT=/absolute/node_modules/playwright \
ALLIM_TEST_CREDENTIALS=/private/fixture-credentials.json \
ALLIM_TEST_URL=http://127.0.0.1:18143 ALLIM_TEST_BROWSER=firefox \
node scripts/check_account_storage_browser.cjs
```

Аналогично запускаются `check_account_import_browser.cjs`,
`check_account_journal_browser.cjs`, `check_account_release_browser.cjs`.
Разные наборы на общих fixture-аккаунтах запускались в отдельных минутных окнах;
серверные ограничения запросов не ослаблялись. Скрипт большой истории получил
тот же параметр запуска Firefox и проверен синтаксически, но замер 10 002 записей
в Firefox в этом аудите не выполнялся.

## Safari: точные границы проверки

Установлен Safari 27.0 (22625.1.29.11.27). `safaridriver` запускается и сообщает
готовность, но создание сессии отклонено: `You must enable 'Allow remote
automation' in the Developer section of Safari Settings`. Настройка не менялась.
Пользователю отправлен запрос включить её; успешной сессии настоящего Safari
в данном аудите не было.

Физический iPhone/iPad через доступные инструменты не обнаружен: USB-список
пустой, `xcrun devicectl` не установлен. Это не доказывает отсутствие устройства
у владельца. Запрошено его участие; результата физической проверки пока нет.

WebKit из Playwright остаётся проверкой движка на Mac. Он не подтверждает
поведение настоящего iOS при выгрузке Safari, блокировке устройства и работе
в фоне. Повторный прогон изменённых скриптов в WebKit прошёл: 20 групп хранения
и 5 групп журнала. Здесь гонка двух первых вкладок не проявилась; отдельное
HTTP-воспроизведение шестью запросами по-прежнему падает. Эти результаты не
делают дефект исправленным. [Сценарий для устройства](ios-device-check.md) подготовлен; доступный
телефону изолированный HTTPS-стенд в этой работе не публиковался.
