# Синхронизация журнала ALLIM — локальный комплект

12 сентября 2026. Код реализован и проверен локально; установка на рабочий сервер и проверка реальных аккаунтов не выполнены.

## Поведение

В раскрываемом «Мой хатм» появился блок «История в аккаунте». До первого подключения журнал хранится только в браузере. Пользователь входит в аккаунт ALLIM и нажимает «Синхронизировать с аккаунтом». После подключения изменения отправляются автоматически с небольшой задержкой. При недоступном сервере запись остаётся локально, интерфейс не выдаёт её за сохранённую в аккаунте.

На новом устройстве пустой журнал получает историю аккаунта. Если и в аккаунте, и локально есть отличающиеся записи, автоматическая замена останавливается. Доступно действие «Сохранить местную копию и загрузить историю аккаунта»: текущая история сначала сохраняется отдельной локальной резервной копией, затем загружается облачная. Сохранённые местные копии доступны по дате и скачиваются как обычные JSON-файлы журнала, пригодные для восстановления. Никакого объединения циклов по совпадению номера без выбора пользователя нет.

После привязки к одному аккаунту журнал не отправляется в другой аккаунт при смене авторизации. Нужно вернуться в связанный аккаунт либо отдельно сохранить нужные копии и очистить местный журнал. Команда «Очистить локальный прогресс» сначала отключает синхронизацию и не удаляет облачную историю. Во время незавершённого запроса очистка блокируется, чтобы исключить гонку с ответом сервера.

## Протокол и защита

Один приватный документ на аккаунт. Владельца определяет только серверная сессия, а переданный `expected_user` служит дополнительной проверкой смены аккаунта. Гость и отключённый пользователь не допускаются. Метод записи — POST, с проверкой CSRF. Ответы запрещено кешировать. Обычные пользователи не имеют прямого доступа к документам через общий API, операции разрешены только через методы журнала.

GET `/api/method/allimquran.reading_journal.load` возвращает текущего пользователя, версию журнала, содержимое и токен текущей сессии. POST `/api/method/allimquran.reading_journal.save` получает `book`, `revision`, `operation`, `expected_user`.

Сервер проверяет схему, типы, реальные календарные даты, диапазоны, повторяющиеся идентификаторы и размер. История является персональным журналом со сведениями пользователя; поле `mic` не является серверным свидетельством качества произношения или достоверности награды. Записи не используются как доверенные финансовые, соревновательные или учебные аттестации.

Сначала блокируется строка аккаунта, затем выполняется актуальное блокирующее чтение журнала. Это защищает и создание первой записи, и конкурентные сохранения. Изменение принимается только при совпадении версии. Повтор последней операции с тем же содержимым возвращает прежнюю версию; переиспользование идентификатора с другим содержимым отклоняется. Более позднее изменение с другого устройства вызывает конфликт вместо перезаписи.

Клиент до отправки сохраняет незавершённую операцию локально. После потери ответа повторяет тот же идентификатор и снимок. Базовая версия сравнивается по SHA-256 канонического JSON. Авторизационные токены в резервные копии и метаданные синхронизации не записываются. Аудио в журнал не передаётся.

## Комплект и установка

Серверные модули находятся в `allimquran/reading_journal*.py`, схема — в `allimquran/allim_quran/doctype/allim_reading_journal/`. Клиентский предпросмотр находится в `companion-workspace/`. Существующая страница `learn` этим коммитом не заменяется.

1. До рабочей установки сделать штатную резервную копию сайта и сначала проверить на стенде.
2. Добавить файлы серверного комплекта в существующий пакет приложения.
3. Из каталога установленного bench выполнить: `bench --site allimquran.com execute allimquran.reading_journal_install.install`.
4. Перезапустить процессы приложения штатным способом, чтобы загрузились новые Python-модули.
5. В комплект страницы чтения включить `reading-sync.js` перед `reading-journal.js`, затем `app.js`. Этот порядок внесён в `companion-workspace/index.html`. Для сайта необходимо отдельно согласовать перенос в актуальные исходники страницы `learn`; автоматической замены действующей страницы здесь нет.
6. Опубликовать обновлённые HTML/CSS/JS по существующему процессу, только после отдельного разрешения владельца.
7. Проверить сценарии ниже с двумя разными аккаунтами и двумя устройствами.

Скрипт установки создаёт схему, но не переносит историю пользователей: привязка выполняется в приложении при явном первом подключении.

## Проверка

Локальные команды из корня проекта:

- `node companion-workspace/tests/reading-journal.test.js`
- `node companion-workspace/tests/reading-sync.test.js`
- `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'test_reading_sync_server.py'`
- `node companion-workspace/tests/reading-journal-ui.test.js`
- `node companion-workspace/tests/reading-sync-ui.test.js`

UI-тесты используют изолированный Chrome и локальный предпросмотр на порту 4187: `python3 -m http.server 4187 --bind 127.0.0.1 --directory companion-workspace`. Установите Playwright или задайте `ALLIM_PLAYWRIGHT_MODULE`; при необходимости задайте `CHROME_PATH`. Проверка синхронизации использует имитацию API: это доказательство логики клиента, а не результат на установленном сервере. Серверные тесты проверяют валидатор, разрешения, CSRF, запросы блокировки, повтор операции и конфликт через адаптер хранилища. Реальные SQL-блокировки должны быть проверены на стенде с двумя параллельными запросами.

Приёмка на стенде: A создаёт запись → второй браузер A получает её; B не видит и не может изменить A; гость не читает журнал; POST без CSRF отклоняется; потеря ответа не удваивает запись; две разные правки одной версии дают один успех и один конфликт; удаление последней записи пересчитывается на втором устройстве; местная очистка не удаляет облачный журнал; выход из аккаунта прекращает отправку.

## Ограничения

- Полная история хранится снимком, максимум 8 МБ JSON на сервере и 100 000 записей. Местная квота браузера может закончиться раньше, особенно с резервными копиями; тогда приложение отклоняет сохранение и показывает ошибку. Потребуется следующий этап — постраничная загрузка сеансов и архивирование, прежде чем обещать неограниченное пожизненное хранение.
- Рабочий reverse proxy может иметь меньший лимит запроса; согласовать его со стендовыми измерениями, не повышать автоматически.
- Конфликт разрешается выбором истории аккаунта с сохранением местной копии. Автоматического слияния отдельных правок и административного восстановления старых облачных версий пока нет.
- Нет фоновой гарантии отправки при закрытой вкладке. Для подтверждения синхронизации нужно увидеть статус сохранения; незавершённый запрос восстанавливается при следующем запуске.
- Реальные авторизация, база, права, резервирование сервера и качество ASR на полном корпусе ещё требуют стендовой проверки. На рабочий сайт этот комплект не устанавливался.
