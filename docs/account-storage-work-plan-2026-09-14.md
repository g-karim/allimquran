**Целевое поведение**

Гость пользуется приложением без регистрации: его личный прогресс хранится в браузере этого устройства. После входа новые изменения автоматически сохраняются в аккаунте на сервере ALLIM. Отдельная кнопка включения синхронизации не нужна. Локальная копия аккаунта и очередь неотправленных изменений поддерживают быстрый интерфейс и работу при пропадании сети; подтверждённый сервером результат считается сохранённым в аккаунте.

Гостевое хранение не является обещанием полностью автономного приложения. Загрузка текста и аудио, а также выбранное серверное распознавание могут обращаться к сети. Сохранение личного прогресса, временная обработка звука и сохранение аудио для проверки — разные действия. Вход в аккаунт сам по себе не включает постоянное хранение всех записей микрофона или участие в исследовательском сборе.

| Сценарий | Ожидаемое поведение |
|---|---|
| Гость | Сохранять локально, явно обозначать режим и предоставлять экспорт |
| Вход без гостевых данных | Загружать аккаунт; далее сохранять автоматически |
| Вход с гостевой историей | Однократно предложить перенос с кратким перечнем данных; до выбора не отправлять эту историю |
| Отказ от переноса | Открыть данные аккаунта; сохранить гостевую историю отдельно |
| Новый телефон после входа | Восстановить поддерживаемый личный прогресс с сервера |
| Пропала сеть | Сохранять изменения на устройстве и показывать ожидание отправки |
| Истекла сессия | Остановить отправку; сохранить очередь с владельцем; возобновить после входа в тот же аккаунт |
| Выход из аккаунта | Остановить операции во всех вкладках, убрать данные аккаунта из интерфейса и вернуться к отдельному гостевому состоянию |
| Смена аккаунта | Загружать данные нового владельца; не переносить историю или очередь предыдущего |
| Очистка данных устройства | Удалять выбранную локальную копию без удаления серверной истории |
| Удаление истории аккаунта | Отдельное явное действие с подтверждением и распространением удаления на устройства |

При выходе по возможности завершать отправку. Если остались неотправленные изменения, предупреждать об этом и сохранять возможность восстановления для того же владельца; не удалять их молча и не превращать в гостевые. Выход не должен зависеть от доступности сервера. Подтверждённый кэш аккаунта очищать при явном выходе. Поведение восстановления неотправленной копии и срок её хранения зафиксировать до реализации; не обещать, что простое разделение ключей браузера защищает данные от владельца самого устройства.

**Что сохраняем в аккаунте**

Объём первой законченной версии — существующий личный прогресс ALLIM и выбранный новый журнал, а не только журнал из PR #1.

| Данные | Правило |
|---|---|
| История чтения, текущий хатм, прошлые хатмы, срок | Сервер для аккаунта; отдельные записи с постоянными идентификаторами |
| Прогресс действующего хифза 300× | Сохранять счётчики и этапы без обнуления; новые действия учитывать с защитой от повторной доставки |
| Очередь повторения и сохранённые аяты | Синхронизировать добавления и удаления между устройствами |
| Дневная цель, активность и итоги занятий | Сохранять; новые итоги рассчитывать по уникальным событиям, старые агрегаты переносить как исходные значения |
| Последнее место чтения | Восстанавливать на другом устройстве; не путать с подтверждённым прогрессом |
| «Аят в жизни»: размышления и действия | Приватные записи владельца; конфликты текста не перезаписывать молча |
| План занятий и вводная диагностика Академии | Единое хранение аккаунта, которое используют и Академия, и страница чтения |
| Общие предпочтения: язык, чтец, параметры чтения | Синхронизировать выбранные пользовательские настройки |
| Курсы, зачисления, заявки и серверные оценки | Использовать существующие записи Frappe/LMS; не создавать параллельную копию |
| Разрешение микрофона, открытое окно, временная запись, кэш текста/аудио | Оставить устройству и текущему сеансу |
| Аудио для проверки, будущие фото Ляуха | Отдельный процесс загрузки приватных файлов, с понятным назначением; Ляух не входит в первый выпуск |
| Согласие на сбор исследовательских записей и его технические токены | Сохранять существующие границы процесса; не включать автоматически и не переносить токены как настройки |

Сохранение результата чтения не превращает его в подтверждённую преподавателем оценку. Различать ручную отметку, автоматическое сопоставление слов и заключение преподавателя.

**1. Зафиксировать состав изменения и исходное состояние**

- Работать от актуального main в отдельной ветке, сохранив незакоммиченные материалы исходной рабочей копии.
- Из PR #1 использовать журнал и проверенные части серверной валидации как основу. Переработать его синхронизацию под автоматическое сохранение всего согласованного прогресса.
- Интегрировать выбранные модули в действующие app-owned исходники learn и Academy. Альтернативный app.js целиком не переносить: он меняет логику распознавания и не использует текущий общий модуль.
- PR #2 сохранить как источник материалов; курс, локализацию и оформление рассматривать отдельными изменениями. Определить место большого архива до форматирования его файлов или объединения с main. Не удалять ветку или материалы на этом этапе.
- Составить точную карту старых ключей и полей, включая quran-companion-prototype-v4, план Академии и allim-academy-diagnostic-v1. Гостевой журнал из локального предпросмотра импортировать только при его фактическом наличии.

Результат: согласованный перечень данных, интерфейсов и переносимых файлов. Вопросы конфликтов исходных PR решаются после определения состава, а не выбором одной версии целого клиента.

**2. Спроектировать единое хранение и обмен изменениями**

- Использовать существующий вход Frappe и определять владельца на сервере по сессии.
- Ввести слой доступа к данным, общий для learn и Academy: гостевой режим и режим аккаунта используют одинаковые операции чтения/записи с разными хранилищами.
- Отделить записи чтения, закладки, очередь, заметки, цели и настройки. Не расширять один огромный JSON-снимок из PR на все данные приложения.
- Предусмотреть схему версии данных, постоянные ID записей, ID операций, версии изменяемых записей и маркеры удаления.
- На устройстве отделять гостевое состояние от данных каждого аккаунта; очередь отправки всегда имеет владельца. Для структурированных данных и очереди использовать IndexedDB; не хранить авторизационные секреты в пользовательских резервных копиях.
- Независимые записи объединять автоматически. Повтор одной операции не создаёт новое чтение и не увеличивает счётчик. Изменение одной заметки с двух устройств сохраняет обе версии до решения пользователя. Правила конфликтов целей и настроек также описать явно.

Результат подготовлен: [контракт данных](account-storage/data-contract.md), [API и таблица конфликтов](account-storage/sync-protocol.md), [переходы пользователя](account-storage/client-lifecycle.md). Карта переноса покрывает все старые поля; примеры протокола и 24 сценария приёмки записаны отдельно. Действующие страницы и сервер на этапе 2 не менялись.

**3. Реализовать серверный слой аккаунта**

- Создать минимальные app-owned схемы и API для выбранных данных с приватным доступом владельца.
- Добавить серверную валидацию, проверку прав и CSRF, ограничение размера, постраничное получение истории и передачу изменений.
- Обеспечить идемпотентность и проверку версии внутри транзакции, включая первое создание данных аккаунта.
- Предусмотреть выгрузку данных, явное удаление и резервное восстановление средствами сайта. Пользовательские удаления должны доходить до других устройств и не воскресать от старого клиента.
- Реализовать подтверждение переноса старых данных без создания вымышленных дат и сеансов. Старые агрегаты сохраняются отдельно от новых событий; неизвестное нельзя достоверно восстановить из счётчика.

Результат выполнен: [сервер и отчёт проверок](account-storage/implementation-stage3.md). API проверен на отдельном Frappe 16 сайте с MariaDB, включая конкурентную доставку, первый вход, права, reset и откат при реальной SQL-ошибке.

**4. Подключить автоматическое сохранение и переходы состояния**

- При запуске определять пользователя до выбора личного хранилища; не показывать гостевой прогресс как историю аккаунта во время загрузки.
- После входа автоматически загружать данные и отправлять новые изменения; отдельного включателя синхронизации нет.
- Показывать понятные состояния: «На этом устройстве», «Сохранено в аккаунте», «Ожидает отправки», «Нужно войти снова», «Нужно выбрать версию».
- Сохранять неотправленные операции до подтверждения сервера, восстанавливать после перезапуска и потери ответа.
- Координировать вкладки и перепроверять владельца/поколение сессии перед отправкой и применением ответа. Смена аккаунта, выход и очистка инвалидируют устаревшие операции. Одного уведомления между вкладками недостаточно для уже выполняющегося запроса.
- Учитывать срок сессии и недоступность сети; отправка после возврата сети возможна только в исходный аккаунт.

Результат выполнен локально: [клиентский слой и проверки](account-storage/implementation-stage4.md). Человек входит и продолжает работу без отдельной настройки синхронизации; очередь привязана к владельцу и сохраняется при потере связи.

**5. Перенести существующие данные без потерь**

- Перед преобразованием сохранить исходную локальную копию и проверить доступное хранилище.
- При первом входе с гостевыми данными показать краткое предложение переноса. Это выбор владельца ранее накопленной истории, а не дополнительный переключатель сохранения новых данных.
- Выполнять импорт повторяемо: один и тот же перенос не удваивает записи и счётчики даже после потери ответа или открытия второй вкладки.
- Если аккаунт уже содержит историю, добавить независимые записи и обработать неоднозначные счётчики/редакции отдельно; не складывать неизвестные накопленные итоги автоматически.
- Оставить исходную копию до успешного подтверждения и проверки результата. Старые данные другого аккаунта никогда не предлагаются как гостевые.
- Обновить чтение данных в обеих страницах, чтобы Академия и Companion показывали одинаковый прогресс.

Результат выполнен локально: [перенос и проверки](account-storage/implementation-stage5.md). Сохранена исходная структура и возможность возврата; тестовые сравнения подтверждают сохранность закладок, заметок, этапов хифза, целей и доступной истории.

**6. Добавить минимальный журнал в текущий интерфейс**

- Оставить прочитанный диапазон, текущий хатм, общий объём повторений, цель к дате и исправление записей.
- Показывать краткий итог рядом с чтением; подробности раскрывать по запросу или в «Прогресс».
- Привязать автоматическое добавление к существующему механизму зачёта, сохраняя его различение ошибки и неопределённости. Повторная доставка результата одного чтения не создаёт новую запись; отдельное повторное чтение учитывается как самостоятельная практика.
- Не менять модель ASR, правила пауз, последовательность слов или обработку границ аудио ради внедрения хранения.
- Отложить счётчик духовной награды, новые методики и обещания персонального планировщика. Они не являются зависимостями журнала или аккаунта.

Результат выполнен локально: [журнал и проверки](account-storage/implementation-stage6.md). Журнал работает для гостя и аккаунта на действующей странице, без подмены клиента на альтернативный из архива.

**7. Проверить целостность и подготовить выпуск**

Обязательные сценарии приёмки:

1. Гость читает, закрывает браузер и видит прежние данные после открытия.
2. Гость входит, переносит историю один раз; повторный вход не удваивает данные.
3. Отказ от переноса сохраняет гостевую копию отдельно и открывает серверные данные.
4. Пользователь A создаёт записи, меняет закладки, хифз и заметки; другой браузер A получает результат.
5. Пользователь B и гость не читают и не изменяют историю A ни через интерфейс, ни через API.
6. Два устройства независимо добавляют записи: обе сохраняются. Одновременная редакция одной заметки не уничтожает одну из версий.
7. Потерянный ответ, повтор запроса и перезапуск вкладки не удваивают события.
8. Работа без интернета сохраняется локально; после входа/соединения отправляется в исходный аккаунт.
9. Очистка устройства, выход, смена аккаунта и восстановление сети в другой открытой вкладке не очищают и не смешивают серверную историю.
10. Задержанный ответ предыдущего аккаунта не меняет данные текущего. Удалённые записи не возвращаются после подключения старого устройства.
11. Перенос сохраняет старые агрегаты честно, без выдуманных чтений; нехватка локального места или ошибка сервера не выдаются за успешное сохранение.
12. Проверены мобильные EN/RU/AR, RTL, настоящий вход Frappe, права API и конкурентные транзакции.

Запустить штатные линтер, форматирование, Python/JavaScript-проверки, сборку и необходимые браузерные сценарии. Регрессии текущего распознавания проверять отдельно от синхронизации; замороженный корпус не изменять для получения более удобного результата. Аудиооценка нужна при фактическом изменении распознавания, а не при каждом изменении настроек хранения.

До production выполнить проверку на отдельном сайте с двумя аккаунтами, резервную копию и репетицию переноса/отката. Откат кода должен сохранять новые серверные записи; не удалять их схемы при возврате предыдущего клиента. Публикация — отдельный этап после результатов приёмки и согласования владельцем, данный план не является разрешением на deploy.

Локальная приёмка выполнена: [отчёт этапа 7](account-storage/release-stage7.md), [24 сценария и границы проверки](account-storage/acceptance-stage7.json). Гонка CSRF исправлена и перепроверена. [Сверка CMS 17 октября](account-storage/cms-reconciliation-2026-10-17.md) перенесла оформление, языки и статьи; дополнительные учебные функции оставлены на следующий этап по выбору владельца. До выпуска нужны завершение согласования CMS/данных, точная целевая конфигурация и физический Safari/iOS.

**Предлагаемое разделение на изменения для ревью**

1. Контракт данных, серверные схемы/API и тесты прав/конкурентности.
2. Общий клиентский слой хранения, вход/выход, автоматическая синхронизация и перенос старого прогресса learn/Academy.
3. Минимальный журнал, встроенный в действующий клиент.
4. Отдельно: курс букв, выбранная локализация/оформление и организация архива PR #2.

Первые три изменения выпускать после совместной приёмки: пользователь не должен получить интерфейс, который обещает перенос всего прогресса, пока часть поддерживаемых данных остаётся только в браузере. Оценку сроков уточнить после контракта данных и проверки доступного тестового сайта.
